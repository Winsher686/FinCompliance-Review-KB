# 电商商品/商家合规审查 · 业务需求与流程设计

> 关联文档：`docs/REFACTOR_PLAN.md`（领域词表 / 规则库 / 文件清单）
> 本文回答两个问题：**要做什么业务（需求）**、**怎么做（流程设计）**。
> 所有流程节点均**对齐现有代码实现**，不是另起架构。

---

## 一、业务背景

**业务方**：电商平台治理团队（自营平台或第三方开放平台）。

**现状痛点**：

| 痛点 | 表现 |
| --- | --- |
| 审核产能不足 | 商品上架/改版量大，人工逐条审标题与详情页不可行 |
| 口径不一致 | 类目规范、广告法、平台规则散落在多个文档，不同审核员判定标准不同 |
| 难以追溯 | 出事后无法回答"当时依据哪一条规则、看了哪份材料判的" |
| 资质核验易漏 | 食品/化妆品/医疗器械等特殊类目需资质，人工比对证照有效期容易漏 |

**系统目标**：把非结构化的商品/店铺/资质/处罚/规则文档，建成**可推理的知识图谱 + 向量库**；
用一套**可配置规则**做自动初审；高风险项**转人工复审**；最终输出**带证据链、可追溯**的合规结论。

---

## 二、业务角色

| 角色 | 职责 | 主要接触 |
| --- | --- | --- |
| 平台治理运营 | 批量提审商品/商家，配置规则阈值 | `POST /review`、导入页 `:8000` |
| 合规审核员 | 处理人工复核队列，通过/驳回结论 | `POST /review/{id}/approve`、审查控制台 `:8002` |
| 商家运营 / 商家 | 查看结论、按建议整改 | 审查报告 |

## 三、业务需求

### 3.1 核心业务需求（BR）

| ID | 需求名称 | 触发场景 | 判定逻辑 | 对应规则 |
| --- | --- | --- | --- | --- |
| **BR1** | 违禁词 / 极限词宣传识别 | 商品标题、详情文案、营销活动页 | 命中禁用词表（"最""第一""国家级""根治""纯天然"等）且无证明材料 | R1 |
| **BR2** | 特殊类目资质核验 | 食品 / 化妆品 / 医疗器械 / 图书等 | 类目 `is_special=true` 但商家无对应有效资质，或资质临近到期/已过期 | R2 |
| **BR3** | 违规处罚未整改追查 | 商家或商品有处罚记录 | 近 N 年存在平台/监管处罚，且未见整改、申诉或下架动作 | R3 |
| **BR4** | 涉诉货源风险预警 | 商品货源来自风险供应商 | 供应商/货源主体为涉诉或失信主体 | R4 |
| **BR5** | 类目错放与价格违规 | 商品类目/价格异常 | 商品属性与所属类目不符；或划线价远高于真实成交价（虚构原价） | R5 |
| **BR6** | 品牌授权链穿透 | 品牌商品 | 存在多层级授权/经销链，用于判断是否获得品牌方正规授权 | R6 |

### 3.2 支撑需求

| ID | 需求 | 说明 |
| --- | --- | --- |
| SR1 | 知识入库 | 商品详情页、店铺资质、违规通知、平台规则可批量导入并建图 |
| SR2 | 主体识别 | 自动识别文档所属**商家/店铺**，作为知识库隔离与过滤维度 |
| SR3 | 多路检索 | 向量 + 稀疏 + 图谱多跳并行召回，RRF 融合 + 精排 |
| SR4 | 证据链 | 每条结论必须挂"图谱路径 / 文档片段 / 关系三元组"证据 |
| SR5 | 人工复核 | 高风险结论强制转人工，复核通过才出正式报告 |
| SR6 | 报告输出 | 结构化 Markdown 报告（对象/结论/证据/风险/建议） |

### 3.3 非功能需求（NFR）

| ID | 需求 | 落地方式 |
| --- | --- | --- |
| NFR1 | **离线可跑** | Milvus / Neo4j / LLM 不可用时，检索/改写/生成走模板兜底，图谱工具返回空结果而非报错 |
| NFR2 | **阈值可配** | 规则阈值全部走环境变量 `COMPLIANCE_*`，不改代码即可调整口径 |
| NFR3 | **结论可溯源** | `evidence_chain` 与 `findings.evidence` 一一对应 |
| NFR4 | **状态可轮询/流式** | SSE 推 `ready/progress/final`，或轮询 `/status/{task_id}` |
| NFR5 | **架构不重构** | 复用 LangGraph 图、8 节点、HITL 中断恢复、三端自包含结构 |

## 四、输入 / 输出契约

### 4.1 审查输入（`POST /review`，字段名沿用现有）

| 字段 | 电商语义 | 示例 |
| --- | --- | --- |
| `company` | **商家 / 店铺名**（主体，= 知识库 `item_name` 维度） | `优选家居旗舰店` |
| `review_type` | 审查类型枚举（见下） | `product_compliance` |
| `question` | 用户问题描述 | `该店铺在售的婴儿奶粉是否存在资质与宣传违规？` |
| `metrics` | 判定基数（经营指标，供规则阈值判定使用） | `{"gmv": 5000000, "listing_count": 320}` |
| `relations` | 可选：上游已装配关系（离线评测用） | — |

**`review_type` 枚举（电商）**：
`banned_word`（宣传违规）｜`qualification`（资质合规）｜`penalty`（违规处罚）｜
`supply_chain`（货源风险）｜`price_category`（类目价格）｜`brand_authorization`（品牌授权）｜
`product_compliance`（商品综合）｜`general`（综合）｜`report`（正式报告）

### 4.2 审查输出

`conclusion`（结论）｜`risk_level`（高/中/低/无）｜`findings`（规则命中）｜
`evidence_chain`（证据链）｜`graph_paths`（图谱路径）｜`report`（Markdown 报告）｜
`needs_human_review` + `approval`（复核信息）

## 五、流程设计

系统由**两条链路**构成，分别是独立的服务单元。

### 5.1 链路 A：知识入库（`:8000`，9 节点）

职责：把商品/店铺/资质/处罚/规则文档转成"向量 + 图谱"。

| # | 节点（文件） | 电商场景职责 |
| --- | --- | --- |
| 1 | `entry_node` | 入口分发：按文件类型决定走 MD / PDF / 转换分支 |
| 2 | `doc_convert_node` | 商品详情页 HTML、店铺页 → Markdown（保留表格与章节） |
| 3 | `pdf_to_md_mode` | 资质证照、处罚决定书 PDF → Markdown（MinerU） |
| 4 | `md_img_node` | 提取商品主图/详情图（对象存储） |
| 5 | `document_spliter_node` | 按**商品属性 / 条款 / 段落**语义切分，注入电商元数据（`doc_type`/`publish_date`/`source`/`chapter`/`clause_no`） |
| 6 | `item_name_recognition_node` | LLM 识别文档所属**商家/店铺名** → `item_name`（知识库隔离维度） |
| 7 | `bge_embedding_chunks_node` | BGE-M3 稠密 + 稀疏双向量 |
| 8 | `import_milvus_node` | 双向量写入 Milvus |
| 9 | `kg_graph_node` | 按电商词表抽取**实体/关系**，写入 Neo4j（含 `SANCTIONED_BY.amount`、`HOLDS_CERT.expire_date` 等关系属性） |

> 第 6、9 节点承载**领域语义**（主体名识别 / 实体关系抽取），词表来自 `knowledge/schema/commerce_domain.py`；其余节点为通用文档处理逻辑。

### 5.2 链路 B：合规审查（`:8002`，8 节点）

职责：把"一个商家/商品的合规问题"变成"有依据、可复核的结论"。

```
                     ┌──────────────────────────────────────────┐
   POST /review  ───▶│ 1. intent_recognize  意图识别              │
                     └───────────────────┬──────────────────────┘
                                         ▼
                     ┌──────────────────────────────────────────┐
                     │ 2. query_rewrite  改写 + HyDE             │
                     └───────────────────┬──────────────────────┘
                                         ▼
                     ┌──────────────────────────────────────────┐
                     │ 3. multi_search  向量/稀疏/图谱 多路检索    │
                     └───────────────────┬──────────────────────┘
                                         ▼
                     ┌──────────────────────────────────────────┐
                     │ 4. rrf_rerank  RRF 融合 + BGE-Reranker 精排│
                     └───────────────────┬──────────────────────┘
                                         ▼
                     ┌──────────────────────────────────────────┐
                     │ 5. evidence_chain  证据链构建              │
                     └───────────────────┬──────────────────────┘
                                         ▼
                     ┌──────────────────────────────────────────┐
                     │ 6. compliance_check  R1–R6 规则判定        │
                     └───────────────────┬──────────────────────┘
                          needs_human_review?
                     ┌───────────────────┴───────────────────┐
                   是 ▼                                    否 ▼
        ┌────────────────────────┐              ┌──────────────────────┐
        │ 7. hitl  人工复核(中断) │              │ 8. report_generate   │
        └───────────┬────────────┘              └──────────┬───────────┘
                    └──────────────▶ 8. report_generate ───┘
                                         ▼
                                        END
```

| # | 节点 | 输入 | 电商场景处理 | 输出 |
| --- | --- | --- | --- | --- |
| 1 | `intent_recognize` | `question` | 归类 `fact/path/compliance/report`；示例换电商（"该店是否有资质？"=fact，"供应商是否涉诉？"=path，"是否违反宣传规范？"=compliance） | `intent` |
| 2 | `query_rewrite` | `question`+`company` | 补全商家/商品名，覆盖六大合规维度（宣传/资质/违规/货源/价格/授权） | `rewritten_query` `hyde_doc` |
| 3 | `multi_search` | 改写后查询 | 并行三路：BGE-M3 向量、稀疏、**图谱多跳**（如"商家→商品→类目→特殊类目→资质"） | `embedding_chunks` `sparse_chunks` `kg_chunks` `kg_triples` `kg_paths` |
| 4 | `rrf_rerank` | 多路结果 | RRF 融合（图谱权重 0.7）→ BGE-Reranker 精排 | `rrf_chunks` `reranked_docs` |
| 5 | `evidence_chain` | 路径/文档/三元组 | 统一组织证据；归一化 `relations`（供规则算金额/比例/日期） | `evidence_chain` `relations` |
| 6 | `compliance_check` | 证据链 + `metrics` | 执行 **R1–R6 电商规则**，汇总风险等级，判定是否转人工 | `findings` `risk_level` `needs_human_review` |
| 7 | `hitl` | 高风险上下文 | `interrupt()` 暂停，抛载荷（风险等级/命中规则/证据摘要）等复核 | `approval` `review_status` |
| 8 | `report_generate` | 全部状态 | LLM 生成报告，失败回退模板 | `report` `conclusion` `review_status` |

### 5.3 条件路由（与现有代码一致）

```python
route_after_compliance(state) -> "hitl" if state["needs_human_review"] else "report_generate"
```

**`needs_human_review` 的判定**（`compliance_check_node._needs_human_review`）：

1. `HITL_ENABLED` 关闭 → 直接 false；
2. `risk_level ∈ HITL_RISK_LEVELS`（默认 `高`）→ **转人工**；
3. `review_type ∈ HITL_REVIEW_TYPES` → **转人工**。

> 电商口径建议：`HITL_REVIEW_TYPES=report,penalty,product_compliance`
> （正式报告、违规处罚认定、商品综合合规——这三类出错代价最高，必须人工把关）。

### 5.4 状态机

```
processing ──(compliance_check: 低/中风险)──▶ completed
     │
     └──(compliance_check: 高风险)──▶ pending_approval
                                          │
                             POST /approve│
                                    ┌─────┴─────┐
                                  通过        驳回
                                    ▼          ▼
                                approved    rejected
```

对应状态字段：`review_status ∈ {processing, pending_approval, approved, rejected, completed, failed}`。

### 5.5 端到端时序（含 HITL）

| 步 | 角色 | 动作 | 系统 |
| --- | --- | --- | --- |
| 1 | 治理运营 | 提交 `POST /review`（商家 + 审查类型 + 问题） | 返回 `review_id` / `task_id` |
| 2 | — | — | 后台跑 8 节点，SSE 推进度 |
| 3 | — | — | 节点 6 命中高风险 → 节点 7 `interrupt` 暂停，状态 `pending_approval` |
| 4 | 审核员 | 前端看到待复核载荷（风险等级 / 命中规则 / 证据摘要） | — |
| 5 | 审核员 | `POST /review/{id}/approve`（通过/驳回 + 意见） | `Command(resume=...)` 恢复图 |
| 6 | — | — | 节点 8 出报告，状态转 `approved` / `rejected` |
| 7 | 商家运营 | 查看报告与整改建议 | `GET /review/{id}` |

## 七、层间边界

**可替换层（领域语义集中在此）**：实体/关系词表 `knowledge/schema/commerce_domain.py`、规则库
`compliance_rules.py`、各节点 prompt 文案、`review_type` 枚举与描述、样例文档、评测集 `knowledge/eval/`、
测试断言、README / `.env.example` / 前端文案。

**稳定层（与业务无关的骨架）**：8 节点逻辑与文件名、`main_graph.py` 拓扑、`route_after_compliance`、
`interrupt`/`Command(resume)` 机制、`ReviewGraphState` 字段结构、`ReviewContext` 结构、API 路由与请求/响应模型、
Milvus / Neo4j 接入、启动脚本。

> 一句话：**流程骨架稳定，业务口径集中在可替换层。**

## 八、验收标准

1. **离线门禁**：`pytest knowledge/test/compliance -q` → **137 passed / 8 skipped**（无 Milvus / Neo4j / LLM 依赖）。
2. **规则评测**：`python knowledge/eval/run_eval.py` → 55 条样本上 `rule_hit_f1` / `risk_level_accuracy` /
   `hitl_accuracy` 均 **100%**；`intent_accuracy` 为关键词兜底口径 **69.1%**（接入 LLM 后由真实意图识别节点计算）。
3. **端到端**：提交一个高风险商家（如"无食品经营资质却售婴幼儿奶粉 + 标题含'最安全'"）→ 命中 R1+R2 → 进入 `pending_approval` → 审批通过 → 出报告。
4. **离线降级**：断开 Neo4j / Milvus 后，审查仍能基于注入关系跑完并给模板报告。
